**Findings:**
- [MINOR] F1 — `backend/app/api/cv_files.py:67` + Starlette formparser: `request.form(max_part_size=1024)` only bounds *non-file* fields (Starlette checks `max_part_size` solely when `_current_part.file is None`). File parts have no per-part or total-body cap, so a client can stream an arbitrarily large body (per part, up to 50 parts) that Starlette spools to a temp file *before* the handler's `file.read(MAX_FILE_BYTES+1)` enforces the 10 MB rule. Functionally correct (verified: 10 MiB oversize test rejects as `FILE_TOO_LARGE`), but it is a resource-exhaustion vector. There is no ingress/ASGI body-size limit in the repo (no nginx/proxy config, no Content-Length guard). Fix (defense-in-depth): reject early on `Content-Length > MAX_FILES * MAX_FILE_BYTES` (or add a body-size middleware / proxy `client_max_body_size`). Can follow up; prod deployment hardening also belongs to T30/T32.
- [MINOR] F2 — `backend/app/services/cv_files.py:67,71` + `_readable_file` (lines 35–47): a re-upload of bytes whose SHA-256 matches a **soft-deleted** record returns a per-file `NOT_FOUND` and no new record is ever created (unique `sha256` + "no silent resurrection"). This is the documented decision in open-questions #31, but it means a file an HR soft-deleted can never be re-added through the UI. Confirm this is intended product behavior (likely fine until a restore/dedupe path exists in a later task); no code change required now.
