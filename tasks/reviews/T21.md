## Findings

- **[BLOCKER] F1 — `backend/tests/api/test_recruitment.py:104-105` (acceptance-criterion test is flaky, fails CI intermittently).**
  The test creates two interviews with the *same* `scheduled_at` (`INTERVIEW["scheduled_at"]` is a fixed constant, reused for round 2 at line 77). It then patches the **first-created** interview (`row`) and asserts `detail["interviews"][0]["feedback"] == "..."`. But `GET /applications/{id}` orders interviews by `(scheduled_at, id)` per spec 03, and on a `scheduled_at` tie the order falls back to the random UUID `id` — so `interviews[0]` is the first-created row only ~50% of the time. Confirmed: 2 pass / 2 fail across 4 runs; failure is `assert None == 'Phản hồi giả'`.
  *Why it matters:* this is the test file that proves the primary acceptance criterion, and the PROGRESS claim "Backend 1052 pass" is not reproducible — CI will go red roughly half the time, so the Definition of Done (green suite) is not actually met. The product ordering itself is correct per spec; only the test's indexing assumption is wrong.
  *Fix:* make the assertion target the patched interview explicitly, e.g. find it by id in `detail["interviews"]` instead of using `[0]`; or give the two interviews distinct `scheduled_at` values so the ordering is deterministic.
